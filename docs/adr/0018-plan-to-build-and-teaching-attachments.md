# 0018. 企劃到實作可一次完成；主線與教學附件分工

- 狀態：已接受（修訂 [0014](0014-portable-usage.md) 決策 2 的「人確認後才動工」；企劃前的需求與資源對齊由 [0036](0036-intake-and-resource-scope.md) 補充）
- 日期：2026-10-02

## 背景

[0014](0014-portable-usage.md) 要求 LLM 填完 `plan.md` 後交人確認才寫 `story.js`。實際使用上，人更常希望 LLM 從企劃一路做到可播放的成品，再看成品修改；只看企劃很難判斷措辭與邏輯是否通順。

`playground/llm-xai-possibilities` 的主簡報做到 18 頁，原因是原理講解與工程展示混在主線。事後把講解頁拆成附件，才發現附件若要教學，「每頁可獨立閱讀」並不足夠，頁與頁之間還要能接成推理；主線則反而不需要。這兩點本可在企劃時決定，事後重排成本高得多。

## 決策

1. **企劃仍先寫，確認改為選擇性**：LLM 先填 `plan.md` 再寫程式；人沒有要求先看企劃時，可以直接接著實作。企劃的價值是逼出敘事骨架，不是當作關卡。
2. **企劃時決定主線與附件**：分鏡表每頁標明放「主線」或「附件」。主線只留案例、結果與產物，可以跳躍；讀懂結果以外的原理放進同一單位的附件（`agentdeck new <name> --related attachments`）。
3. **教學附件要接成邏輯鏈**：附件從一個問題出發，每頁交代得到什麼、還缺什麼，下一頁補上缺口；術語先定義再使用；最後一頁回答開頭的問題。分鏡表多寫「留下的缺口」欄。
4. **實作後由 LLM 做一次邏輯審查**：逐頁讀標題、引言、重點與細節，檢查主線順序、引用到已移走內容的地方、附件鏈是否斷裂，以及文字與版面、資料是否相符，修正後再交付。

## 理由

- 骨架便宜但影響全局，措辭與通順度只能看成品判斷：先寫企劃、再迭代成品，比在企劃上停下來等確認更符合實際。
- 主線聽眾要的是「做得到什麼」，附件讀者要的是「為什麼」，兩者節奏不同；混在一起時兩邊都變差。
- 邏輯審查原本靠人事後覺得不對才觸發，固定成流程的一步成本很低。

## 後果

- 方向錯誤可能到成品階段才被發現；人想先把關時，仍可要求先看 `plan.md`。
- 附件與主簡報可能互相連結；閱讀器目前不支援連到指定頁，連結只能指向附件入口。

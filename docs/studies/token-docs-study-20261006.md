# HTML PPT token 優化第二輪：無損文件去重

## 最終決定

使用者決定沿用原本流程。本輪差異小且受工具呼叫次數影響，不足以支持切換；不採用文件去重工具，繼續直接使用原本的 `agentdeck docs <名稱>`。去重工具與樣本僅保留為實驗紀錄，不納入正式流程。上游CLI、AGENTDECK.md與框架原本就未改動，無須回退。

## 結果與採用判斷

兩對、四個 fresh subagent 的完整製作實驗中，去重組平均總 token 為659,664，原始組693,999，**觀察到少4.95%**；平均時間167.78對167.55秒，沒有加速。四份簡報都通過相同 V1／V2／離線驗收，父代理查看四份 V2 結果截圖，文字、數值、最高者與版面完整。

值得保留無損去重這個小工具，但**不能宣稱它穩定節省5%**：第一對工具呼叫數相同，總 token 少0.91%；第二對去重組少一次工具呼叫，總 token 少8.82%。Agent 行為與重試不是完全固定的，第二對的差異不能全歸因於文件長度。每個條件只有兩個樣本，未做統計顯著性推論。

## 控制與量測範圍

- 任務延續[第一輪](token-cost-study-20261006.md)：六頁合成「資料檢核試驗」，V1 A60/B75/C90、C最高；V2改B95、B最高。流程、分工、下一步相同。
- 同模型 `gpt-6-astra`、同 effort `low`，fresh context，不繼承父對話歷史。第一對 a1→b1，完成後第二對 b2→a2；同對並行。a為原始文件，b為去重文件。代理只收到sample ID，沒有預期節省率。
- 父代理統一透過CLI init/new/add/vendor準備四個獨立單位，提供相同plan、入口引用與已驗證的check.cjs，story仍是blank。這些共同準備成本另列，**本輪不是完全從零成本，也不與第一輪直接計算改善率**。
- 唯一刻意變更是 component-docs.txt：flow/table/bars/steps/figure 的完整CLI文件，共用相同尾段只出現一次。兩組完整讀同一AGENTDECK規則與catalog；未修改必讀規則。檔案去重可逐字還原每份原文件，不是摘要或删掉限制。
- 原始文件含相同逐元件標題6,509字元，去重版4,202字元，少2,307／35.44%。第一輪原始6,415未加這些標題，所以分母不同。**字元數不是模型token數。**
- 共用QA保留V1快照、逐頁導覽、每頁兩句講稿、數值／圖表比例／最高者、主控台與版面檢查、真實1.2秒等待後截圖。解壓ZIP後封鎖HTTP(S)，file://重驗。四份check檔案hash相同；同條件的兩份元件文件hash相同。

## 失敗、干擾與品質邊界

- a1、b1、b2遇到同一路徑delete/add的apply_patch拒絕，改用UTF8寫檔；都保留在成本中。
- a2第一次讀檔未指定UTF8而重讀；a2、b2先讀錯plan位置後更正。這表示即使有相同明確指示，agent執行仍有變異。
- 所有共同驗收第一次執行就通過，沒有父代理要求返工。子代理各查看V1/V2/offline三張圖；父代理另查看四組V2圖。
- 只驗證本合成案例與1440×1000桌面；不涵蓋手機、互動、語音、完整Siguard或其他模型。
- 無法清除／控制服務端快取，反轉順序只能降低部分順序偏差。未快取下降不能單獨證明文件造成的節省。

## 對下一步的意義

文件雖少35.44%，它只占整個agent上下文的一部分。本輪原始組每個usage事件平均約5.2～5.4萬總token；額外一次往返的量級就可能超過文件去重的收益。這是觀察上的量級比較，不是「刪一次呼叫一定省固定數字」的因果估計。

因此保留文件去重作局部改善；若要更大幅降低成本，下一個候選應是重用已驗證的製作／檢查流程、減少工具失敗與無效往返。這些候選尚未由本輪隔離實驗證明，不能用跨輪差額代替證據。尚未修改上游CLI、AGENTDECK.md或框架。

# 工程可能性展示指引（建議）

適合技術可能性、PoC 與方案比較：讓聽眾看見某項能力如何接到工作流程、目前做到哪裡、下一步要驗證什麼。這是寫作建議，資料契約與標記仍依 `AGENTDECK.md`；不要求新增框架 API 或通用元件。

## 先做能證明用途的一頁

在 `plan.md` 寫下使用者的工作、目前卡住的決策、可取得的資料與預期工程產物。先做最有說服力的一個真實案例，實際操作確認後再展開整份簡報。

建議順序：**真實案例 → 可操作結果 → 工程產物 → 尚未驗證的部分**。

| 段落 | 要讓人看到什麼 | 例：模型判讀巡檢 |
| --- | --- | --- |
| 真實案例 | 可辨識的輸入與具體失敗 | 同一張手寫數字，模型認成哪個數字 |
| 可操作結果 | 改一個條件，輸入、中間證據與輸出同步對照 | 切換樣本，並列直接判讀、模型輸出與 XAI 證據 |
| 工程產物 | 結果可以接到哪個下一步 | 下載含案例 ID、證據與待驗證假設的巡檢工單 |
| 尚未驗證 | 哪項觀察還不足以支持結論，以及如何補驗 | 用新樣本檢查工單是否幫助找到可重現的錯誤 |

只補足讀懂結果所需的原理。名詞介紹、完整訓練課程與預測題不是必要頁型；失敗案例也可以支撐展示，但要交代它是自然取得或刻意挑選。

## 主線與附件分工

主線精簡：只留案例、可操作結果、工程產物與待驗證，頁與頁可以跳躍，不必環環相扣。原理、方法比較、判讀限制等教學內容放進同一單位的附件（`agentdeck new <name> --related attachments`），從主線相關頁的 `detail` 連入，附件設 `back` 返回。在 `plan.md` 分鏡就標好每頁放哪裡，事後再拆要重排整份。

教學附件要接成邏輯鏈，「每頁能獨立閱讀」並不足夠：

1. 封面提出一個問題，例如「模型把這張 5 判成 3，要有哪些證據才能除錯？」
2. 每頁先交代得到什麼，再寫還缺什麼；下一頁的引言接住這個缺口。
3. 術語先定義再使用，不要讓後面的頁假設讀者已經懂。
4. 結論寫「學到什麼」，不沿用主線展示能力的語氣。
5. 最後一頁回答開頭的問題，並指回前面哪幾頁提供了答案。

文字不要寫版面位置，例如「左上那張」；資料排序或版面一變就會錯。

## 實作後的邏輯審查

企劃可以一路做到成品（ADR 0018），交付前逐頁讀一次標題、引言、重點與細節：

- 主線：順序是否一路擴大（單一案例 → 一批資料 → 接入系統），沒有在單張與整批之間來回跳。
- 拆走頁面後：留下的頁是否還引用已移走的內容或概念，例如資料規模、術語。
- 附件：每頁的缺口是否由下一頁補上，結尾是否回答了開頭的問題。
- 數字與描述：是否和資料、版面一致。

## 同一案例比較不同路徑

- 用穩定的 `caseId` 對齊輸入、各方法輸出、證據與分析。切換一次案例，所有面板一起更新；顯示目前案例與共同條件。
- 同時保留原始證據與解讀。例如原圖、模型分數、熱圖、遮擋前後的數值，與建議工單並列，讓人能判斷解讀是否有根據。
- 缺結果就顯示缺結果。不同模型、版本、輸入條件或人工替代值應在結果旁交代，避免把不一致的資料呈現成同條件比較。
- 一頁可承載完整巡檢操作；背景與結論另拆頁。工程產物可用本地資料下載，無須為展示另建服務。

## 工程產物要能追溯

下載的工單、報告或設定檔會離開簡報，被另存到任意位置。產物本身要帶足夠資訊讓人回查：

- 寫入案例 ID、產生時間、資料版本與產生方式（實測、回放、模擬、作者分析）。
- 證據引用用相對於主題資料目錄的路徑，另附一個 `evidence_base` 說明這些路徑以哪個位置為基準（例如相對簡報入口）；不要寫本機絕對路徑，也不要假設下載檔旁邊有證據檔。
- 尚未驗證的假設、限制與不允許的自動行為（例如不自動改標籤）寫成欄位，不只寫在頁面說明。
- 頁面寫明只產生本機檔案、沒有送往外部服務；若是示範格式，產物內也標示。
- 檢查時實際產生一次產物，解析內容並逐筆確認證據路徑存在。

## 說清楚結果從哪裡來

對結果就近註明來源與產生方式，必要的版本、執行條件及資料位置放在 `detail` 或主題製作紀錄。以下是寫作檢查，不是新的資料型別。

| 內容 | 標示重點 |
| --- | --- |
| 實測 | 執行了什麼、用哪個資料與版本、觀察到什麼 |
| 人工資料 | 哪些值由人填入或挑選，用於展示何種情境 |
| 作者分析 | 誰根據哪些證據提出解讀；助理撰寫的文字也屬於此類，不等於另跑模型 API |
| 構想 | 尚未實作的行為、預期輸入輸出與待驗證條件 |

互動沿用 `agentdeck docs visual-story` 的區分：**即時計算、預先計算結果回放、模擬**。操作會重新計算什麼就寫什麼；切換圖片或載入既有結果不表示模型重新推論。回放可以展示工程用途，模擬可以說明預期流程，都不能替代實測效益。

解讀要指向可檢查的證據與假設，例如用遮擋前後的分數變化檢查某區域對判讀的影響。沒有做過的驗證放到工單或下一步，不寫成已完成結果。

## 動態結果與現場編輯

回放與計算結果預設不可編輯；固定的作者說明可以標 `data-edit`，但互動更新只操作結果容器，不替換可編輯說明或其父容器。元件已有編輯開關時使用既有開關。

需要按案例記錄註記時，由主題用 `caseId` 保存並交代保存期限與匯出方式。頁面 ID 與 `data-key` 不能自動提供案例層級的註記保存；單用頁面的 `state` 也不代表已持久保存。

## 最小驗收

1. 每個案例的輸入、方法結果與證據對得上；缺值與人工替代值有明示。
2. 操作、來源標示與實際運算一致；工單或其他產物能開啟並追溯案例。
3. 改固定說明後切換案例、換頁再返回，人工修正仍在；案例註記不互相覆蓋。
4. 在實際閱讀器內檢查起始狀態、縮圖、換頁返回與離線播放；無法操作時仍有可理解的靜態說明。

完成時分開回報資料檢查與實際播放檢查。展示能成立不等於已證明省時、準確或改善決策；效益要有相應實測才下結論。

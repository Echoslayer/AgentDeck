# Repo 目標導向探索：目錄地圖與重要檔案閱讀卡片（建議）

適合「我想在某個 repo 完成特定工作，但不知道該讀到哪裡」的探索與貢獻入門。以讀者的目標評估閱讀範圍，產出可逐層探索的 AgentDeck。這是寫作指引與 prompt 範本；簡報單位、檔案所有權、元件與播放契約仍依 `AGENTDECK.md`。

## 可直接使用的 prompt

填入 repo、目標與輸出位置，其餘有需要再補。將以下內容交給能讀取本機 repo 的 agent：

```text
請依 AgentDeck 的 repo-explorer 指引，製作一份目標導向的 repo 探索簡報。
先讀 AgentDeck 的 AGENTDECK.md，再用 CLI 的 docs repo-explorer 讀完整指引。

來源 repo：<路徑>
探索目標：<我想理解／修改／貢獻的具體功能或工作>
目前背景：<熟悉哪些語言、工具或概念；未知可省略>
暫不深入：<本次不想先學的部分；無則省略>
AgentDeck 位置或 CLI：<本機路徑或可用指令>
獨立簡報輸出位置：<路徑>/<主題名稱>
語言：<預設繁體中文>

請實讀 repo 的指引、目錄、文件與關鍵程式碼，建立「為了這個目標，
我該讀哪些地方、讀多深、何時才需要其他部分」的地圖。
完整交代第一層資料夾，繼續評估第二層與重要第三層；必要的功能路徑再往下追。
除了主要程式碼，也評估 CI、建置、設定、測試、文件、打包、共用底層等範圍。

至少有一頁可逐層點選的目錄地圖。每個目錄顯示功能、閱讀級別、
需要深入的情境、建議入口；支援返回、麵包屑、搜尋與閱讀級別篩選。
重要檔案以目錄說明中的可展開閱讀卡片呈現，不混進資料夾導覽。
卡片說明職責、何時讀、起讀函式／類別／設定區塊，以及可接著看的實作或測試。
先串通代表性任務路線，不為了湊檔案數量而擴充。

來源 repo 只讀。已有足夠資訊就開始製作；只問會改變方向的必要問題。
依實際來源標明版本、涵蓋範圍與未確認事項。完成播放與離線驗證，
清除交付目錄裡的驗證截圖、報告、臨時腳本與解壓副本，再交付入口及 ZIP。
```

本機 AgentDeck 上游的 CLI 是 `node cli/agentdeck.mjs`；下游依 `agentdeck/agentdeck.json` 的 CLI 欄位。例：在上游執行 `node cli/agentdeck.mjs docs repo-explorer`。

## 1. 先建立評估視角

把目標改寫成「具備哪些背景的讀者，要在這個 repo 完成什麼工作」，記入 `plan.md`。例如「熟悉 Python 的開發者要貢獻 DataFrame API」，比「理解 Spark」更能決定閱讀範圍。

- 從對話與來源取得已知條件；缺少且會改變方向的目標、背景或輸出位置才詢問。
- 「暫不深入某語言」是閱讀優先順序。若真實功能路線跨到該語言，要標出邊界與觸發條件。
- 先找來源與輸出位置的 `AGENTS.md`／`CLAUDE.md`，再遵守適用的專案指引。
- 記錄來源 commit／版本、日期與相關未提交變更。髒工作樹的內容不能只標成該 commit 的版本。
- 探索來源預設只讀；不因整理地圖而切換來源分支、修改程式碼、執行昂貴測試或安裝套件。需要擴大操作時依既有授權處理。

## 2. 先盤點，再沿任務追查

第一層逐項列出，一個資料夾一筆，不把多個項目合併成含糊的一列。第二層做功能評估，重要第三層繼續展開；若第三層仍只有 `src/main` 之類容器，就補具體入口或沿必要路線深入。

| 範圍 | 要回答的問題 |
| --- | --- |
| 目標功能與公開 API | 使用者從哪裡進入？介面、實作與實際執行各在哪裡？ |
| 測試與測試支援 | 對應案例在哪裡？fixture／基底、測試 runner 分別負責什麼？ |
| CI 與開發工具 | 哪裡選擇測試、準備環境與執行 lint/build？失敗該追哪個入口？ |
| 建置、依賴與設定 | 哪個檔案是啟動器、哪個定義模組、哪個只是設定範本？ |
| 文件、範例與打包 | 公開行為要同步更新什麼？開發依賴與發行依賴如何區分？ |
| 共用底層與其他模組 | 哪些由目標功能直接使用？什麼問題才會跨到這裡？ |

用目錄清單、README、manifest、代表性實作、呼叫端與測試交叉核對。不能只憑 `common`、`tools`、`config` 這些名字猜用途，也不能把 API 包裝層當成全部實作。

在地圖或製作紀錄中說清楚涵蓋範圍：第一／第二／第三層各涵蓋多少，哪些更深路徑額外展開。排除 `.git` 內部資料、生成物、套件快取等噪音時交代規則。區分「沒有子目錄」與「還有子目錄但未展開」，不把截斷範圍畫成空目錄。

## 3. 用四級表達閱讀深度

以下是對指定讀者與目標的建議，不是模組品質或價值排名：

| 級別 | 讀到什麼程度 | 判斷條件 |
| --- | --- | --- |
| 深入讀 | 能解釋目標輸入、實作與測試如何連起來 | 直接承擔本次目標的行為 |
| 會操作 | 找得到入口、會使用、會定位錯誤 | 貢獻過程常用，但不必先理解工具全部實作 |
| 按需追 | 碰到具體邊界再深入相應部分 | 執行引擎、協定、部署、型別或跨模組依賴 |
| 先略過 | 本次沒有前置閱讀需求 | 任務尚未涉及，之後遇到明確情境再回來 |

每個評估附上理由與升級條件，例如「改 Python API 通常不用讀；worker 啟動失敗時再追這個模組」。避免只給顏色、分數或「很重要」。子目錄可以沿用上層條件，但須表明是繼承的判斷，不能偽裝成逐檔深讀的結論。

## 4. 目錄導覽與檔案卡片分開呈現

建議一頁承載完整探索：資料夾列表負責下鑽，詳情區負責功能、閱讀建議與重要檔案。窄螢幕可上下排列。選用元件前依 `AGENTDECK.md` 查看 catalog；現有元件無法完整表達時，在主題內自製。

**目錄節點**保存 repo 相對路徑、功能、閱讀級別、需要深入的情境、子目錄及來源入口。介面需有麵包屑、上一層、搜尋、清除條件、結果數與空結果說明；說清楚搜尋和篩選的作用範圍。

**檔案卡片**放在目前目錄的閱讀區，用不同外觀區分。預設顯示檔名與一句職責，展開後包含：

- 何時讀、讀到什麼程度。
- 從哪個函式、類別、測試案例或設定區塊開始；可附核對過的快照行號。
- 下一站：對應實作、呼叫端、協定或測試，並說明為何接著看。
- repo 相對路徑與必要的版本資訊。

展開卡片不切換目錄、不增加麵包屑，也不把檔案計入資料夾數。只有明確按「下一站」才導航；抵達後展開目標卡片。返回目錄或換頁後保留合理的閱讀狀態。可用原生 `details/summary`，保持鍵盤操作、焦點可見及內容可捲動。

檔案卡片是閱讀提示，不必複製整份原始碼。實讀並核對起點、路徑與下一站；沒有證據的內容標為待查，不生成看似精確的函式名或行號。一般入口可只保留路徑，無須全部做成卡片。

## 5. 用任務路線決定何時補內容

優先串通二至三條與目標相關的路線，例如：

1. 改 API：公開介面 → 實作／橋接 → 具體測試 → 測試 runner。
2. 追 CI：失敗檢查 → workflow／job → 執行命令 → 設定或依賴。
3. 跨執行邊界：client 計畫 → 協定 → server／worker → 結果或錯誤處理。

這些是閱讀順序；只有實讀證明是執行呼叫鏈時，才標成呼叫關係。測試基底不能取代具體測試案例；路線停在 helper 時，考慮補一個實際案例。

先以少量代表檔案走通路線。只在路線斷掉、遇到新邊界或讀者選定新功能時擴充，不設定必須湊滿的檔案數或整個 repo 覆蓋率。

## 6. 做成 AgentDeck 並交付

依 `AGENTDECK.md` 使用 `init`／`new` 建立獨立單位，先填 `plan.md`。可以安排封面、互動地圖、閱讀級別、代表路線與結尾；不要把每個資料夾拆成一張投影片。已有輸出目錄時先看現有入口與所有權，選擇不覆寫既有內容的位置。

主題資料與說明存於單位內，播放不依賴來源 repo、本機絕對路徑或網路。目錄與檔案共用同一份受控資料，避免搜尋、計數與詳情各持有不同副本。展示的是來源快照，不宣稱會自動追蹤 repo 更新。

互動頁提供能獨立閱讀的 `previewArt` 與 `mount` 清理函式。固定作者文字可編輯，動態目錄與卡片不能覆寫人工修正。HTML 保留互動；靜態 PDF／PPTX 的呈現與進階輸出仍依 `AGENTDECK.md`，不承諾原生 PPT 保留任意下鑽功能。

改版時保留人維護的 `edits.js`，先讀註解。使用者要求「先 commit 再試」時，先確認 Git 狀態，只提交本次範圍作為基線，再做試改；不順便提交其他工作或推送。

## 最小驗收與乾淨交付

- **來源**：顯示的目錄／檔案存在，涵蓋數與實際清單一致；起讀符號、行號及下一站可核對。
- **互動**：下鑽、返回、搜尋、篩選、清除與空結果可用；卡片展開不改目錄身分，鍵盤可操作，下一站正確。
- **版面與狀態**：桌面與窄螢幕可讀，展開內容可看完；換頁返回後狀態正確，固定文字的人工修改保留。
- **離線**：雙擊入口可用、沒有缺失資源或主控台錯誤；打包後另驗一次互動與連結。
- **交付整潔**：驗證截圖、JSON 報告、臨時腳本與解壓副本不留在交付內容中。製作時依 `AGENTDECK.md` 放置檔案，交付前把需要保留的檢查工具移存製作紀錄區，清除臨時產物，再打包；核對 ZIP 也沒有夾帶。用於解說本身的插圖與正式附件則保留。

最終提供入口、離線包、來源版本、涵蓋範圍與實際完成的驗證。只在使用者要求或既有授權涵蓋時提交／發布。

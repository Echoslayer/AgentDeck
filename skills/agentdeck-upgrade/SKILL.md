# AgentDeck 更新

把既有簡報更新到已確認的目標版本，保留客製行為。使用者要求「最新版」時更新核心、已安裝元件與必要的契約接入；要求指定功能時，只處理該功能及其依賴。不要為了升級重寫內容、套用新品牌，或替所有頁面新增可選的口語稿、錄影步驟、PPT 輸出。

## 1. 確認單位與更新來源

- 找到目標簡報的 `agentdeck/agentdeck.json`，讀其 `cli`、`source` 與單位內 `agentdeck/AGENTDECK.md`。舊佈局可能只有根 `agentdeck.json` 或 `AGENTDECK.md`。遵守檔案所有權；這份 skill 補充更新流程。
- 本機 CLI 可用 `node "{{AGENTDECK_HOME}}/cli/agentdeck.mjs"`；預設來源為 `github:Echoslayer/AgentDeck`。沿用簡報指定的 fork／來源，不自行換回官方。
- 「最新版」須確認該來源的遠端預設分支 HEAD，記下完整 commit。以該 commit 的乾淨 checkout 執行 CLI，或使用固定 commit 的 `npx -y github:Echoslayer/AgentDeck#<完整 commit> <指令>`（fork 換成其來源）。同一次更新固定使用這個目標。不要直接 pull 或 reset 使用者的上游 checkout。
- 本機未提交版本或固定 tag 不等於遠端最新版。使用者指定本機來源時照做並記錄；無法連線確認時說明限制，不宣稱已是最新版。目標比簡報契約舊時不降版。
- 先在目標簡報單位執行 `<CLI> update core --check`，讀取來源、契約與差異摘要；可更新回傳 0，受阻回傳非 0。相容且無本地衝突時直接更新，不必讀核心完整原始碼或 patch。只有核心衝突才執行 `<CLI> diff core --patch`；要求更新元件時另以 `status`／`diff <name>` 篩選需要處理的元件。`diff --patch` 是目前上游與本地的差異；記錄的基準是雜湊，並不包含舊檔案。需要三方比對時，從原始來源與已記錄 commit 取得舊版；取不到就逐項理解差異，不假設能自動合併。

## 2. 保留還原點，決定改動

- `update core` 會在首次寫入前自動備份完整單位至系統暫存目錄，包含未追蹤／忽略檔，並印出備份位置；記錄該位置，無需重複備份。若在核心更新前就要修改內容、元件或搬移舊單位，先自行建立完整外部備份。暫存備份需長期保留時移到持久位置；不要以會丟失現有工作的方法清理 git。
- 純核心更新由 CLI 自動核對非核心一般檔案的原始 SHA-256，包含 `edits.js`；無需另寫一次檢查腳本。需要修改內容或元件時，另記錄每份 `edits.js` 的 SHA-256，盤點頁面 ID、元件 key、品牌、相關入口與既有互動（含 `pages/`）。
- 跨契約時依序讀 `<CLI> docs <n>-to-<n+1>`，以實際說明決定是否可就地更新。契約 0／1 的舊目錄依文件 `init` 新單位再搬移，不能直接 `update core --migrate`。
- 指定功能：從目標版 `AGENTDECK.md`、`docs <元件或指引>` 與實作確認接入條件，列出必要核心、元件與頁面改動。沒有專用指南時先查實作，不捏造指令或欄位。
- 保留內容、版面、互動與人工修正已在更新要求的範圍內，可直接進行。只有無法兼顧的行為衝突才提出具體選項；其餘獨立工作繼續。

## 3. 執行更新

| 對象 | 處理 |
| --- | --- |
| 核心副本 | 無本地修改時執行 `update core`；跨契約且文件允許就地更新時加 `--migrate`。核心有修改／刪除時先讀差異，能用主題或自製元件保留的行為先移出核心，再以 `--force` 更新。仍會失去行為時，說明衝突並取得取捨，不盲目強制覆蓋。 |
| 已安裝元件 | 逐個讀新版 `docs <name>` 與差異。未客製的以 `add <name> --force` 更新；已客製的先在單位外完成合併，再以 `add <name> --force` 取得新版基準與依賴，最後疊回合併結果及相應 README。合併後 `diff` 顯示本地修改是正常的。上游已移除的元件需保留或替換並驗證，不能直接刪除。 |
| 自製元件、入口、story.js／pages、CSS | 依遷移文件與功能接入要求修改，保留客製行為、頁面 ID 與元件 key；檢查動態產生的標記及選擇器，不只替換初始 HTML。 |
| 品牌與 edits.js | 保留原檔，不吸收或清空人工修正。若新格式確實要求修改，指出需要的具體轉換並取得授權；單純要求升到最新版不視為授權改寫人工修正或品牌。 |

不要手改 `agentdeck.json` 的版本或基準來消除差異。只透過 CLI 維護記錄；新增外部套件仍依 `AGENTDECK.md` 的授權規則處理。核心更新後重新讀新版 `AGENTDECK.md`，完成所有必要的簡報接入。

## 4. 驗證與交付

- 搜尋遷移文件指定的舊 API／路徑殘留；執行 `status`、`diff`，逐項解釋保留的客製差異。
- 相容的純核心更新：確認 CLI 雜湊檢查通過，執行已有課程檢查，主簡報及附件各驗證載入、翻頁，並操作本次更新功能。不必一律逐頁驗收。跨契約、修改內容或涉及全頁渲染時，才擴大為逐頁播放，核對 `edits.js` SHA-256、主控台、縮圖、圖片、附件、連結及人工修正對應。
- 操作互動頁，切換參數／案例、換頁再返回；確認客製行為與更新功能正常。已有語音／動作時驗證其選擇器和播放；不要為驗收產生未要求的新內容。
- 執行 `pack`，解壓到單位外另一位置，以離線播放方式檢查入口與實際依賴。CLI 成功、契約一致或打包成功都不代表播放已通過；無瀏覽器等限制時明列未驗證項目，回報「更新已套用，驗證未完成」。
- 最後回報：來源與目標 commit／契約、已更新的功能與元件、保留的客製差異、驗證結果、交付與備份位置、尚待決定的衝突。所有必要接入與驗證通過才稱「更新完成」。

目前 CLI 的 `status` 沒有內容遷移完成狀態；`update core` 寫入新契約只表示核心已更新，不可當成整份簡報完成的證據。
